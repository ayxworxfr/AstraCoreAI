# 子系统设计方案

> 本文档汇总三个已实施的核心子系统设计：Memory 系统重设计、Skill 系统重设计、Multi-Agent 并行执行。
> 每个子系统均已完成实现（✅），文档作为设计决策的历史存档。

---

## 一、Memory 系统重设计（Context Engineering 架构）

> 状态：已实施 ✅

### 1.1 设计背景

原 Memory 系统存在四个根本性缺陷：

| 缺陷 | 具体表现 |
|------|---------|
| **注入位置单一** | 所有 scope 的记忆统一拼成文本块追加到 system prompt 末尾，用户画像和临时会话状态竞争同一槽位 |
| **检索不懂语义** | `_rank_memories()` 用正则拆词做关键词匹配；问"游戏状态板"，记忆里写"游戏棋盘"，完全召不回来 |
| **每轮只提取一条** | `_extract_with_llm` 返回单个决策，同一轮对话的多个可提取事实全部丢弃 |
| **use_count 字段废弃** | 字段记录了访问次数，但从未驱动任何决策；高价值 session 记忆无法晋升 |

### 1.2 核心架构：两级注入

#### Tier-1：稳定用户画像（→ System Prompt）

```
System Prompt
  ├── AI Identity（角色定义）
  ├── Skills（技能清单）
  └── [Tier-1] User Profile          ← user + global scope，全量加载
      • preference（用户偏好）
      • constraint（行为约束）
      • decision（已确认决策）
      • procedure（AI 行为规范）
```

- 来源：`scope = user | global`，`status = active`
- 加载方式：SQL 全量查询（条目少，通常 < 50 条）
- 字符预算：800 字符（超出按 importance 截断）
- 频率：每次对话的 `prepare()` 阶段执行一次

#### Tier-2：动态会话上下文（→ 合成消息对）

```
[...对话历史]
user:      "[记忆同步]"           ← 合成桥接消息，不持久化
assistant: "【记忆快照】\n         ← Tier-2 内容，不持久化
            ### 当前会话状态
            - ...
            ### 项目约束
            - ..."
user:      <真实用户消息>         ← 持久化
```

- 来源：`scope = session | project`，`status = active`
- 检索方式：Chroma 向量相似度（按当前消息语义检索）
- 字符预算：1200 字符（top-8 相关记忆）
- 合成消息标记 `metadata = {"synthetic": True}`，在 `_prepare_for_save()` 中过滤，绝不写入持久化历史

### 1.3 Memory Type

| type | 说明 | 天然归属 |
|------|------|---------|
| `fact` | 稳定事实 | Tier-1 / Tier-2 |
| `preference` | 用户偏好 | Tier-1 |
| `decision` | 已确认决策 | Tier-1 / Tier-2 |
| `constraint` | 约束或禁止事项 | Tier-1 |
| `state` | 当前状态 | Tier-2 |
| `plan` | 后续计划 | Tier-2 |
| `summary` | 阶段摘要 | Tier-2 |
| `lesson` | 经验教训 | Tier-1 / Tier-2 |
| `procedure` | AI 行为规范（新增） | Tier-1 |

### 1.4 向量检索层

- **Collection**：`astracore_memory`，`all-MiniLM-L6-v2` 嵌入，cosine 距离
- **同步策略**：Chroma 是索引，SQLite 是 source of truth；增删改必须两端同步
- **降级策略**：Chroma 不可用时 `_available=False`，Tier-2 回退到 SQL ILIKE，Tier-1 不受影响

### 1.5 批量记忆提取

每轮对话结束后异步提取，使用 `_ExtractionBatch` schema：

```python
class _ExtractionBatch(BaseModel):
    memories: list[_MemoryDecision]   # 0-N 条，支持 create / update / ignore
```

流程：`_extract_with_llm()` → 去重检查 `_consolidate_candidate()` → `create/update_memory()` → `upsert Chroma`

### 1.6 LLM 记忆晋升（Session → User）

**触发条件（启发式预过滤）**：
```python
should_evaluate = (
    memory.scope == MemoryScope.SESSION
    and (memory.use_count >= 5
         or (memory.importance >= 4 and memory.use_count >= 3)
         or memory.locked)
)
```

**LLM 决策输出**：`promote_user / promote_project / keep / archive`

晋升本质是**复制 + 归档**，不删除原始记忆，保留溯源链路。晋升在 `_after_run()` 后台任务中执行，不阻塞对话响应。

## 二、Skill 系统重设计

> 状态：已实施 ✅（2026-06-01 完成）

### 2.1 设计背景

原系统本质上是**命名 System Prompt 注入机制**，存在三个根本问题：
- 角色与能力概念混用，用户只能"选一个"，无法组合
- 服务端路由是反模式：Claude 完全看不到路由决策过程，服务端用 ML 模型模仿 Claude 的推理是多余的一层
- 用户自建 Skill 锁在数据库里，无法与支持 Agent Skills 标准的工具互通

### 2.2 核心设计

**Skill = 能力包（Capability Package）**：Skill 不再定义"角色"，而是定义"能力"——专业操作步骤、可引用文档、可执行脚本。Claude 通过 System Prompt 中的摘要清单**自主决策**加载哪些 Skill。

**三层 System Prompt 结构**：

```
Layer 1：身份层（始终注入）
  ai_name / owner_name / 基础人格 / 全局指令
────────────────────────────────────────────
Layer 2：Skill 摘要清单（始终注入）
  所有可用 Skill 的 name + description，约 50-100 token/skill
  Claude 据此自主决策加载哪个 Skill
────────────────────────────────────────────
Layer 3：动态上下文（按需注入）
  RAG 检索结果 / 记忆引擎内容
```

**废弃服务端 Skill Routing**：`skills/router.py` 整个模块删除。

### 2.3 Skill 格式规范（兼容 Agent Skills 开放标准）

```
skill-name/
├── SKILL.md          ← 必须：YAML frontmatter + Markdown 正文
├── scripts/          ← 可选：可执行脚本（Python / shell）
├── references/       ← 可选：参考文档（按需加载）
└── assets/           ← 可选：模板、静态资源
```

SKILL.md 关键 frontmatter 字段：`name`、`description`、`metadata.category`、`metadata.order`

### 2.4 三个 Skill 工具

| 工具 | 功能 |
|------|------|
| `load_skill(skill_id)` | 返回完整 instructions + 引用列表 + 脚本列表 |
| `get_skill_reference(skill_id, file)` | 读取 references/ 下的参考文档 |
| `run_skill_script(skill_id, script, args)` | 在沙箱内执行脚本（30s 超时，防路径穿越） |

### 2.5 Skill 续接机制

检测到活跃 Skill 后，向消息栈注入合成的续接提醒，确保多轮对话中 Claude 不遗忘当前技能规范（见 `pipeline.py → _detect_active_skill()`）。

### 2.6 用户自建 Skill

- **UI 编辑器（简单模式）**：前端表单创建，存储为 DB 记录，无脚本支持
- **文件系统目录（高级模式）**：`config.yaml` 配置 `skills.extra_dirs`，支持完整目录结构
- **导出**：UI 创建的 Skill 可导出为标准 Agent Skills zip，兼容 Claude Code、Cursor 等工具

## 三、Multi-Agent 并行执行

> 状态：已实施 ✅

### 3.1 设计背景

LLM 推理本身是串行的，面对"对比 A 股和美股表现"这类多数据源查询，瓶颈不在工具执行，而在 LLM 推理串行。目标是实现 **Orchestrator-Worker 并行 Agent 模式**。

### 3.2 执行流程

```
用户消息: "对比今天 A 股和美股表现"
    │
    ▼
Orchestrator LLM（使用用户选定主模型）
    │ 调用 spawn_agents([taskA, taskB])
    ▼
ParallelAgentTool
    asyncio.gather(agentA, agentB)
    ├── Worker Agent A（查 A 股）  独立 LLM + ToolLoop + SessionState
    └── Worker Agent B（查美股）  独立 LLM + ToolLoop + SessionState
    并发流式输出 AGENT_* 事件
    │ 聚合结果
    ▼
Orchestrator LLM 综合两份结果，流式输出最终回答
```

### 3.3 Worker 隔离规则

| 属性 | 规则 |
|------|------|
| LLM 实例 | 每个 Worker 独立 |
| ToolLoopUseCase | 每个 Worker 独立，最多 5 轮 |
| SessionState | 全新，不携带主会话历史 |
| 可用工具 | 全量工具减去 `spawn_agents`（防递归，深度上限 = 1） |
| Model | 用户当前 profile，可被 `model_profile` 字段覆盖 |
| 并发数 | 2–5 个（`tasks` 数组限制） |
| Worker 超时 | 60s（独立于父级 ToolLoop） |

### 3.4 SSE 事件扩展

新增 6 种 `AGENT_*` 事件类型，所有事件 `metadata` 包含 `agent_id`：

| StreamEventType | SSE 事件名 | 含义 |
|---|---|---|
| `AGENT_START` | `agent_start` | 子 Agent 启动 |
| `AGENT_TEXT_DELTA` | `agent_message` | 子 Agent 文本增量 |
| `AGENT_THINKING_DELTA` | `agent_thinking` | 子 Agent 思考增量 |
| `AGENT_TOOL_CALL` | `agent_tool_start` | 子 Agent 工具调用 |
| `AGENT_TOOL_RESULT` | `agent_tool_result` | 子 Agent 工具结果 |
| `AGENT_DONE` | `agent_done` | 子 Agent 完成 |

### 3.5 前端展示：SubAgentPanel

```
┌─ ⚡ 并行处理中 (2 个 Agent)  ──────────────────────────────────┐
│  ┌── Agent 1 ──────────────────┐  ┌── Agent 2 ─────────────┐  │
│  │ 📋 查 A 股今日行情           │  │ 📋 查美股今日行情       │  │
│  │ ▸ search_astock    ✓ 0.8s  │  │ ⟳ search_nasdaq        │  │
│  │ 上证指数 3,245 (+0.82%)    │  │ 🤔 分析中...            │  │
│  └─────────────────────────── ┘  └─────────────────────────┘  │
│  全部完成 · 共耗时 3.2s（串行约需 6.1s）                       │
└────────────────────────────────────────────────────────────────┘
```

SubAgentCard 自动折叠规则：运行中展开，完成后折叠，用户手动点击优先级最高。

### 3.6 配置开关

```yaml
agent:
  enable_spawn_agents: true   # false 时不暴露 spawn_agents 工具给 LLM
```

### 3.7 性能预期

| 指标 | 串行 | 并行 |
|------|------|------|
| 典型双查询耗时 | ~12s | ~6s |
| LLM API 并发数 | 1 | N+1（N Worker + Orchestrator 综合）|
| Token 消耗 | 基准 | 略增（子 Agent 有独立 system prompt）|
