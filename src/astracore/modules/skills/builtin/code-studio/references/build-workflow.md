# /build 工作流

按 plan 文件逐步执行编码，实时更新进度。

---

## 检查门（执行任何步骤前，两项必须全部通过）

**检查门 1**：定位 plan 文件

- 用户指定文件名（如 `/build add-user-auth`）→ 读取 `.claude/astra/plans/*add-user-auth*.md`
- 未指定 → 读取 `.claude/astra/plans/` 下**最近修改**的 `.md` 文件
- 文件**不存在** → 阻断，输出：`⚠️ 未找到 plan 文件，请先运行 /plan <任务描述> 制定开发计划。`

**检查门 2**：验证 plan 状态

- 读取 plan 文件顶部 `status` 字段
- `status: confirmed` 或 `status: in-progress` → 通过
- 其他值（`draft` / `done` / 缺失）→ 阻断，说明原因：
  - `draft`：计划尚未确认，提示用户先确认 plan
  - `done`：计划已完成，询问"是否重新执行？"
  - 缺失：文件格式错误，展示文件内容让用户核查

## 执行步骤

### 步骤 1：展示任务总览，确认开始

```
即将执行开发计划：<任务标题>

待完成步骤：
  [ ] 1. ...
  [ ] 2. ...
  [ ] 3. ...

验证命令：make test

确认开始执行？
```

### 步骤 2：更新 plan 状态为 in-progress

将 plan 文件顶部 `status` 修改为 `in-progress`。

### 步骤 3：逐步执行

对每个未完成的步骤（`[ ]`）：

1. 告知用户当前正在执行哪一步
2. 执行对应操作（读文件 → 写代码 → 修改文件）
3. 执行完成后：
   - 将 plan 文件中对应 `[ ]` 改为 `[x]`
   - 简要报告该步骤结果（改了哪个文件 / 新增了什么）

**执行原则**：
- 只修改 plan 文件"影响文件"列表中明确列出的文件
- 超出范围的修改 → 停下告知用户，确认后再继续
- 每步之间不需要用户确认（除非遇到阻断条件）

### 步骤 4：遇到阻断立即停

以下情况立即停止执行，**不得继续下一步**：

| 阻断条件 | 处理方式 |
|---|---|
| 执行报错（非预期的编译/运行错误） | 在 plan 文件对应步骤后追加 `> ⚠️ 错误：[描述]`，等待用户指令 |
| 发现影响范围超出 plan 预期 | 告知用户，列出受影响的额外文件，询问是否继续 |
| 遇到需求歧义（不知道该写什么） | 提问，等待用户答复 |
| 依赖文件不存在 / API 不符合预期 | 告知实际情况，不得自行猜测补全 |

### 步骤 5：全部完成后运行验证

所有步骤标记 `[x]` 后：

1. 读取 PROJECT.md 中的测试/lint 命令
2. 执行验证命令
3. 根据结果：
   - **通过** → 更新 plan `status` 为 `done`，输出完成摘要
   - **失败** → 展示错误，在 plan 文件末尾追加错误记录，等待用户指令

---

## 完成摘要格式

```
✅ 开发计划执行完成：<任务标题>

完成步骤：
  [x] 步骤 1
  [x] 步骤 2
  [x] 步骤 3

验证结果：所有测试通过，无 lint 错误

Plan 文件：.claude/astra/plans/YYYY-MM-DD-<slug>.md（status: done）
```

---

## 错误记录格式（追加到 plan 文件末尾）

```markdown
## 执行日志

- YYYY-MM-DD HH:MM — 步骤 2 执行失败
  > ⚠️ 错误：ImportError: cannot import name 'X' from 'module.y'
  > 状态：等待处理
```
