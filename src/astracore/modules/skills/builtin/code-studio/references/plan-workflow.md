# /plan 工作流

制定开发计划，生成持久化的 plan 文件。`/build` 依赖此文件执行。

---

## 前置处理

读取 `.claude/astra/PROJECT.md`：
- **存在** → 继续
- **不存在** → **自动执行 /init 工作流**（加载 init-workflow.md 完成全部步骤），生成 PROJECT.md 后继续 /plan，无需用户手动触发

---

## 执行步骤

### 步骤 1：解析任务描述

从用户输入提取：
- **任务目标**：要实现什么（功能 / 修复 / 重构）
- **任务类型**：`新功能` / `Bug 修复` / `重构` / `文档` / `其他`
- **已知约束**：用户已明确的限制（如"不改数据库"、"修UT不改业务代码"）

如果任务描述**过于模糊**（如 `/plan 优化代码`）→ 反问：
```
任务描述需要更具体，请补充：
1. 要优化哪个模块或功能？
2. 当前有什么问题（性能 / 可读性 / 结构）？
3. 期望优化到什么程度？
```

### 步骤 2：探索相关代码

基于任务描述，读取相关文件（**最多 10 个**，优先核心路径）：
- 如果有对应的 `/explore` 报告（`.claude/astra/explore/` 下），**优先读取报告**替代重新探索
- 读取前列出文件清单，确认后再读

目标：识别以下内容：
- **影响文件**：哪些文件需要新增 / 修改 / 删除
- **依赖关系**：改动会影响哪些下游调用方
- **验证方式**：现有测试覆盖了哪些路径

### 步骤 3：生成计划草稿

按模板生成计划，展示给用户审阅（此时 `status: draft`，**不写入文件**）：

```
已生成开发计划草稿，请确认：

## 任务：<标题>
目标：...
影响文件：...
步骤：
  [ ] 1. ...
  [ ] 2. ...
验证命令：...

回复"确认"开始保存，或直接告诉我需要修改的地方。
```

### 步骤 4：按用户反馈修改草稿

- 用户指出修改点 → 更新草稿，重新展示
- 循环直到用户确认

### 步骤 5：写入 plan 文件

用户确认后：
1. 将 `status` 设为 `confirmed`
2. 生成 slug：将任务标题转为 kebab-case（英文 / 拼音均可）
3. 写入 `.claude/astra/plans/YYYY-MM-DD-<slug>.md`
4. 告知用户文件路径，提示可用 `/build` 开始执行

---

## Plan 文件模板

```markdown
---
status: confirmed
created: YYYY-MM-DD
task: 任务标题（中文）
---

# 开发计划：<任务标题>

## 目标

[1-3 句话：要实现什么，完成标准是什么]

## 影响文件

| 文件路径 | 变更类型 | 说明 |
|---|---|---|
| `path/to/file` | 新增 / 修改 / 删除 | 具体变更内容 |

## 实现步骤

- [ ] 步骤 1：[动词起手，具体动作]
- [ ] 步骤 2：[动词起手，具体动作]
- [ ] 步骤 3：[动词起手，具体动作]

## 验证

```bash
# 运行验证命令（来自 PROJECT.md）
make test
```

预期：[验证通过的标准，如"所有测试通过，无新增 lint 错误"]

## 注意事项

[潜在风险 / 边界情况 / 需要特别关注的点，没有则填"无"]
```

---

## slug 命名规则

| 任务标题 | slug |
|---|---|
| 添加用户认证 | `add-user-auth` |
| 修复登录超时 bug | `fix-login-timeout` |
| 重构 RAG 检索模块 | `refactor-rag-retrieval` |
| Add OAuth Support | `add-oauth-support` |

- 中文 → 意译为英文 kebab-case
- 空格 / 特殊字符 → 用 `-` 替代
- 长度 ≤ 40 字符
